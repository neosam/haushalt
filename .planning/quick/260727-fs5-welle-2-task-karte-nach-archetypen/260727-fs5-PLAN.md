# Quick 260727-fs5: Task-Karte nach Archetypen (Welle 2)

Welle 1 hat das *Formular* nach Archetypen umgebaut, Welle 1c den Bonus-Typ ergänzt. Die *Liste*
sieht noch für jeden Typ gleich aus: dieselbe `−` / `n/m` / `+`-Reihe, egal ob es um eine
Steuererklärung, einen Rückfall oder einen gemeldeten Verstoß geht.

Kernanliegen des Mockups (Schritt 3): **„Der Knopf sagt, was er tut"** — und der tote `−`-Knopf
verschwindet. Heute ist er für die zuständige Person eines Instandhaltungs-Tasks dauerhaft
`disabled` mit einer Erklärung im `title`-Attribut, das auf dem Handy unsichtbar ist.

## Design-Vorgaben aus dem Mockup

| Typ | Knopf | Akzent |
|-----|-------|--------|
| Aufgabe | „✓ Erledigt" (primär) | primary |
| Routine | Zähler `−` `1/2` `+` | success |
| Gemeinsame Aufgabe | „✓ Hab ich gemacht" (primär) | #0ea5e9 |
| Schlechte Angewohnheit | „Rückfall eintragen" (warn) | warning |
| Instandhaltung (andere) | „Verstoß melden" (danger) | danger |
| Instandhaltung (zuständig) | **kein Knopf**, Zustand im Klartext | danger |

## Eigene Entscheidungen (nicht im Mockup)

1. **Bonus** kommt im Mockup nicht vor (ist jünger). Knopf „✓ Gemacht" (primär), Akzent violett
   (`--primary`-nah, aber eigener Ton), Zähler `3 ×` — bereits in 260727-fcg umgesetzt.
2. **Zähler vs. Einzelknopf** entscheidet das Ziel, nicht der Typ: bei `target_count > 1` braucht
   es die Feinsteuerung, sonst genügt ein Knopf. Eine Routine mit Soll 1 bekommt also „✓ Erledigt",
   eine gemeinsame Aufgabe mit Soll 3 den Zähler. Der Archetyp bestimmt nur *Beschriftung und
   Farbe*, nicht die Bauform — sonst verlöre ein Typ mit Soll 3 seine Bedienbarkeit.
3. **Rücknahme beim Einzelknopf:** Das Mockup zeigt nur den unerledigten Zustand. Ein zusätzlicher
   Rücknahme-Knopf erscheint, sobald es etwas zurückzunehmen gibt *und* der Nutzer darf. So geht
   keine Funktion verloren, ohne dass ein Knopf ins Leere zeigt.
4. **Statustext ohne Namen:** Das Mockup schreibt „zuletzt gestern von Anna". `TaskWithStatus`
   kennt `last_completion` (wann), aber nicht *wer* — die Person müsste die API erst mitliefern.
   Der Text nennt deshalb Anzahl und Zeitpunkt und lässt den Namen weg, statt die API in einem
   Karten-Task zu erweitern.

## Tasks

### Task 1 — Karten-Modell als reine Funktionen

**Files:** `frontend/src/components/task_card_model.rs` (neu), `components/mod.rs`

Analog zu `task_form_model.rs`: keine Signals, kein DOM, läuft unter `#[test]` auf dem Host.

- `enum CardAction { Counter, Single { label_key, style }, Locked { completions }, ReadOnly }`
- `enum ActionStyle { Primary, Warn, Danger }`
- `card_action(archetype, target_count, completions, can_uncomplete, is_completable_by_user)`
  - nicht bedienbar → `ReadOnly`
  - `!can_uncomplete && completions > 0` → `Locked` (der Fall des toten Knopfes)
  - `target_count > 1` → `Counter`
  - sonst → `Single`
- `accent_class(archetype) -> &'static str` — CSS-Modifier `task-item--<typ>`
- `type_badge(archetype) -> Option<(&'static str, &'static str)>` — Icon + i18n-Key; `None` für
  OneOff und Routine (die brauchen kein Etikett, sie sind der Normalfall)

**Verify:** `nix develop -c cargo test -p frontend task_card_model`

## must_haves

**Truths:**
- Für die zuständige Person eines Instandhaltungs-Tasks gibt es keinen deaktivierten Knopf mehr,
  sondern den Grund im Klartext
- Jeder Archetyp hat eine erkennbare Beschriftung und einen Farbakzent
- Ein Task mit Soll > 1 behält den Zähler, unabhängig vom Typ
- Keine Bedienfunktion geht verloren: Rücknahme bleibt erreichbar, wo sie erlaubt ist
