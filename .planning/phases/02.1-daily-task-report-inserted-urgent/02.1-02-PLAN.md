<objective>
Create the shared response type and the report service's testable core: timezone-aware date
resolution, the "Due today" section, the shared line formatter, empty states, and the full text
layout. The "Missed yesterday" section is stubbed to an empty list here and filled in by plan 03 —
so the formatter and both empty states are already provable in this plan.

Purpose: RPT-01 and RPT-04. D-19 puts all logic in a service so it is unit-testable; D-01 puts
text generation in the backend, always English, deliberately bypassing frontend i18n because a
future phase will feed this text to an LLM (D-02: keep it stable and machine-parseable).

Output: `shared::DailyReportResponse`, `backend/src/services/report.rs` with
`generate_daily_report(...)` plus inline tests, registered in `services/mod.rs`.
</objective>

<pitfalls>
- **Do not call `tasks::get_due_tasks`.** D-05 rejects it: it uses `Utc::now().date_naive()` (UTC,
  not household timezone). It stays untouched; the report computes its own due-today set.
- **Do not call `scheduler::today_in_timezone`.** It hardcodes `Utc::now()` internally.
- **Do not use a raw `task_completions WHERE due_date = today` check for the D-07 done marker.**
  `scheduler::get_next_due_date`'s `Weekdays` (lines 187-211) and `Custom` (lines 213-226) branches
  deliberately SKIP today even when today is a scheduled occurrence — `test_get_next_due_date_weekdays`
  asserts "When completing on Monday, should get NEXT Monday, not today". So a Weekdays/Custom task
  completed today can be stored with a future `due_date`. Mirror `get_task_with_status`'s
  period-bounds computation instead; that is also what the Tasks page shows, so the report stays
  visually consistent.
- **`list_tasks` does not filter `paused` or `assigned_user_id`** — apply D-14's paused filter and
  D-13's ownership rule yourself.
</pitfalls>
