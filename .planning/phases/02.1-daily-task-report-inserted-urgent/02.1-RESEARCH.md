## User Constraints (from CONTEXT.md)

### Locked Decisions

**Purpose & Language (drives several decisions below)**
- **D-01:** The report text is **generated in the backend** and is **always English**, regardless of the UI language. Reason stated by the user: in a later version the text will be sent to an LLM automatically. For now, the user only wants to copy it manually. Do **not** route the text through the frontend i18n system.
- **D-02:** Keep the text format stable and machine-parseable (fixed section headers, one task per line). It is a human-readable report today and an LLM prompt payload later.

**Data Source — "Due today"**
- **D-03:** Compute live from the task list using `scheduler::is_task_due_on_date(task, today)`.
- **D-04:** "Today" is resolved in the **household timezone** (from `household_settings.timezone` via `scheduler::parse_timezone` / `scheduler::today_in_timezone`), **not** UTC.
- **D-05:** The existing `GET /households/{id}/tasks/due` endpoint (`tasks::get_due_tasks`) stays untouched — it uses `Utc::now().date_naive()`, which is a pre-existing inaccuracy. The report gets its own, correct computation in the new report service. (Fixing `get_due_tasks` is a deferred idea, see below.)
- **D-06:** Inverted habits (bad habits, `habit_type.is_inverted()`) are **not** listed in the "due today" section at all — "due" makes no sense for something you are supposed to avoid.
- **D-07:** Tasks already completed today **remain listed** in the "due today" section, marked as done. *(Claude's discretion on the exact marker — proposed: a `(done)` suffix on the line.)*

**Data Source — "Missed yesterday"**
- **D-08:** Read from the **`missed_task_penalties` table** (`task_id`, `due_date = yesterday`), not from a live recomputation. Rationale: the report should show what the system actually penalized.
- **D-09:** Only entries for which a **penalty was actually applied** count as missed. For inverted habits the background job awards a *reward* for not doing them, so rows in `missed_task_penalties` belonging to inverted habits are **excluded**.
- **D-10:** **Additionally**, inverted habits that *were performed* yesterday are listed as missed — the user's rule is "everything that went wrong yesterday belongs in there". These do **not** appear in `missed_task_penalties`; they are `task_completions` rows with `due_date = yesterday` on a task whose `habit_type` is inverted.
- **D-11:** Both sources go into **one single section** ("Missed yesterday"), without separate sub-labels. *(User: "Lass es erst mal in einer.")*
- **D-12:** "Yesterday" is likewise resolved in the household timezone.

**Scope — "my tasks"**
- **D-13:** A task counts as the user's own if `assigned_user_id == current_user` **or** the task has no assignee (unassigned tasks hit every household member in the background job, so they hit the user too).
- **D-14:** Exclusions mirror the background job: archived tasks, paused tasks, and pending suggestions are excluded everywhere. In the "missed yesterday" section, one-time tasks (`RecurrenceType::OneTime`) and household vacation days are additionally excluded.
- **D-15:** Note for the planner: `missed_task_penalties` has **no `user_id`** column. The per-user filter must be applied by joining to `tasks` and applying the D-13 rule. Do not add a column / migration for this phase.

**API**
- **D-16:** **One** endpoint, `GET /households/{id}/report`, returning both sections in a single response.
- **D-17:** Response body carries **only the generated text**, e.g. `{ "report_text": "..." }`. No structured task lists. New shared type in `shared/src/types.rs`.
- **D-18:** Strictly today/yesterday — **no** `?date=` parameter.
- **D-19:** Report logic lives in a backend **service** (`backend/src/services/`) with unit tests, per RPT-04; the handler stays thin.

**Text Format**
- **D-20:** Line format (not prose sentences), section headers followed by `- ` bullets:
  ```
  Daily report — Kitchen — Sat, 2026-07-26

  Due today:
  - Empty the dishwasher
  - Take out the trash
  - Clean the litter box (by 20:00)

  Missed yesterday:
  - Vacuuming
  ```
- **D-21:** Per task, show the **title plus the deadline time if `due_time` is set** — no points, no category.
- **D-22:** Section order: "Due today" first, "Missed yesterday" below.
- **D-23:** Empty states, English, per section:
  - Due today → `No tasks scheduled for today`
  - Missed yesterday → `All tasks completed yesterday`

  Both sections are always rendered, each with its own empty-state line — there is no combined "everything empty" variant.

**Frontend**
- **D-24:** New household tab at `/households/:id/report`, label **"Bericht"** (de) / **"Report"** (en), positioned **directly after "Aufgaben"/Tasks** in the tab bar. Wire through `HouseholdTab` enum, `HouseholdLayout` active-tab detection, `app.rs` route, and the `tabs.*` i18n keys.
- **D-25:** **Read-only** view. No completing, no opening the task modal, no links to tasks.
- **D-26:** The page renders the backend text block verbatim (preformatted / whitespace-preserving) plus a **"Kopieren" / "Copy" button** above it that puts the text on the clipboard. No Web Share API.
- **D-27:** Tab label and copy button are translated (de/en) as usual — only the **report text itself** is English-only.

- Date navigation (`?date=` parameter, browsing older reports) — deliberately out of scope.

## Summary

This phase is almost entirely **internal composition**: every piece of logic the report needs (timezone-aware "today"/"yesterday" resolution, due-date matching, habit inversion, vacation-mode awareness, household membership authorization) already exists in `backend/src/services/scheduler.rs`, `background_jobs.rs`, `household_settings.rs`, and `tasks.rs`. The only genuinely new technical surface is (1) a new backend service+handler+shared-type triplet following the exact layering already used by `statistics.rs`, and (2) a **browser Clipboard API** integration on the frontend, which does not exist anywhere in this codebase yet and requires two new `web-sys` Cargo features.

Reading the actual source (not the project's own `CLAUDE.md`/`STRUCTURE.md` descriptions, which are partially stale) surfaced several concrete landmines that would otherwise cause silent test failures or incorrect report content: the shared test harness (`test_utils.rs`) is missing the `missed_task_penalties` table entirely and has a `household_settings` table with 16 of 22 production columns missing (so `household_settings::get_or_create_settings` — which the report needs for timezone/vacation data — will fail against it as-is); the documented `AuthenticatedUser` extractor does not exist anywhere in the code (the real pattern is a manual `extract_user_id` + `is_member` check repeated in every handler); and there is no SQLx compile-time-macro usage anywhere in the backend, so `cargo sqlx prepare` is **not** part of this phase's workflow despite `SQLX_OFFLINE=true` being set in the Nix shell. A more subtle finding: `scheduler::get_next_due_date`'s `Weekdays` and `Custom` branches deliberately skip "today" when today is itself a scheduled occurrence, which means `task_completions.due_date` for those two recurrence types can diverge from the actual calendar day of completion — this affects how the "done" marker (D-07) and the D-10 raw-`due_date` check should be implemented.

**Primary recommendation:** Build `backend/src/services/report.rs` with a single testable entry point `generate_daily_report(pool, household_id, user_id, now_utc: DateTime<Utc>) -> Result<String, ReportError>` (mirroring the existing `is_task_overdue(task, due_date, timezone, now_utc)` "inject the moment, resolve timezone internally" pattern from `scheduler.rs`), reuse `tasks_service::list_tasks` + manual D-13/D-14 filtering for "due today" (not `get_due_tasks`, per D-05), and read `missed_task_penalties` + `task_completions` directly (not a live recomputation) for "missed yesterday", per D-08. Before writing report-service tests, extend `test_utils.rs` with the missing table and columns (Wave 0 gap, detailed below).

### Pattern 1: Thin handler + testable service (mirrors `statistics.rs` / `household_settings.rs`)
**What:** Handler extracts user, checks membership, calls one service function, maps `Result` to HTTP status. All logic and all tests live in the service.
**When to use:** Always, per this codebase's established convention (verified in every handler file read).
**Example:**
```rust
// Source: pattern verified in backend/src/handlers/statistics.rs:34-97
// backend/src/handlers/report.rs (NEW)
use actix_web::{web, HttpResponse, Result};
use shared::ApiError;
use uuid::Uuid;

use crate::models::AppState;
use crate::services::{households as household_service, report as report_service};

pub fn configure(cfg: &mut web::ServiceConfig) {
    cfg.service(web::scope("/report").route("", web::get().to(get_report)));
}

async fn get_report(
    state: web::Data<AppState>,
    req: actix_web::HttpRequest,
    path: web::Path<Uuid>,
) -> Result<HttpResponse> {
    let user_id = match crate::middleware::auth::extract_user_id(&req, &state.config.jwt_secret) {
        Ok(id) => id,
        Err(_) => {
            return Ok(HttpResponse::Unauthorized().json(ApiError {
                error: "unauthorized".to_string(),
                message: "Invalid or missing token".to_string(),
            }));
        }
    };
    let household_id = path.into_inner();

    if !household_service::is_member(&state.db, &household_id, &user_id).await.unwrap_or(false) {
        return Ok(HttpResponse::Forbidden().json(ApiError {
            error: "forbidden".to_string(),
            message: "Not a member of this household".to_string(),
        }));
    }

    match report_service::generate_daily_report(&state.db, &household_id, &user_id, chrono::Utc::now()).await {
        Ok(report_text) => Ok(HttpResponse::Ok().json(shared::ApiSuccess::new(shared::DailyReportResponse { report_text }))),
        Err(e) => {
            log::error!("Error generating daily report: {:?}", e);
            Ok(HttpResponse::InternalServerError().json(ApiError {
                error: "internal_error".to_string(),
                message: "Failed to generate report".to_string(),
            }))
        }
    }
}
```
Then wire it in exactly like every other domain (verified in `backend/src/handlers/households.rs:7,30-43`):

### Pattern 2: Injectable "now", timezone resolved inside the service (testability)
**What:** Public entry points that depend on "today" take `now_utc: DateTime<Utc>` as an explicit parameter and resolve the household-local date **inside** the function body, rather than calling `Utc::now()` or `scheduler::today_in_timezone()` (see Common Pitfall #5) internally.
**When to use:** Any new function whose behavior depends on "today"/"yesterday", per the project's own v1.1 decision ("pass current_date to functions under test — no global time mocking", `.planning/STATE.md` Accumulated Context) and directly precedented by `scheduler::is_task_overdue`.
**Example:**
```rust
// Source: precedent is backend/src/services/scheduler.rs:341 (is_task_overdue signature)
// backend/src/services/report.rs (NEW)
pub async fn generate_daily_report(
    pool: &SqlitePool,
    household_id: &Uuid,
    user_id: &Uuid,
    now_utc: DateTime<Utc>,
) -> Result<String, ReportError> {
    let settings = household_settings::get_or_create_settings(pool, household_id).await?;
    let tz = scheduler::parse_timezone(&settings.timezone);

    // NOTE: do NOT call scheduler::today_in_timezone(tz) here — it hardcodes Utc::now()
    // internally (scheduler.rs:326-328) and would make this function untestable with a
    // pinned date. Replicate its one-line body with the injected `now_utc` instead:
    let today = now_utc.with_timezone(&tz).date_naive();
    let yesterday = today - chrono::Duration::days(1);

    let household = households::get_household(pool, household_id)
        .await?
        .ok_or(ReportError::HouseholdNotFound)?;

    let due_today = build_due_today_section(pool, household_id, user_id, today).await?;
    let missed_yesterday = build_missed_yesterday_section(pool, household_id, user_id, &settings, yesterday).await?;

    Ok(format_report(&household.name, today, &due_today, &missed_yesterday))
}
```
In a test, this is pinned with e.g. `Utc.with_ymd_and_hms(2026, 7, 26, 10, 0, 0).unwrap()` — no global clock mocking required, consistent with the rest of the Phase 2 test suite.

### Pattern 3: "Due today" section — reuse `list_tasks`, apply the filters it does NOT apply
**What:** `list_tasks` already excludes archived tasks and non-approved suggestions (verified query, `tasks.rs:376-392`), but does **not** filter by `paused` or by `assigned_user_id` (verified — no such clause in its `WHERE`). The report must apply D-13/D-14's remaining filters itself.
**Example:**
```rust
// Source: backend/src/services/tasks.rs:376-392 (list_tasks query, read directly)
async fn build_due_today_section(
    pool: &SqlitePool,
    household_id: &Uuid,
    user_id: &Uuid,
    today: NaiveDate,
) -> Result<Vec<ReportLine>, ReportError> {
    let tasks = tasks_service::list_tasks(pool, household_id).await?; // already: !archived, approved-only

    let mut lines = Vec::new();
    for task in tasks {
        if task.paused { continue; }                                    // D-14 — list_tasks does NOT filter this
        let is_mine = task.assigned_user_id.map(|id| id == *user_id).unwrap_or(true); // D-13
        if !is_mine { continue; }
        if task.habit_type.is_inverted() { continue; }                   // D-06
        if !scheduler::is_task_due_on_date(&task, today) { continue; }   // D-03

        let done = is_completed_for_today(pool, &task, today).await?;    // see Common Pitfall #6 — NOT a raw due_date=today check
        lines.push(ReportLine { title: task.title, due_time: task.due_time, done });
    }
    // Sort by due_time ascending (None last, i.e. treated as end-of-day), then title — see Open Question #2
    lines.sort_by(|a, b| a.due_time.cmp(&b.due_time).then_with(|| a.title.to_lowercase().cmp(&b.title.to_lowercase())));
    Ok(lines)
}
```

### Pattern 4: "Missed yesterday" section — read materialized state, do not recompute
**What:** Per D-08, do not re-derive "was this missed" — read `missed_task_penalties` (already-applied penalties) and separately `task_completions` (D-10's inverted-habit-performed case). Join to `tasks` for the D-13/D-14 filters (`missed_task_penalties` has no `user_id`, D-15).
**Example:**
```rust
// Source: mirrors the fetch-broad-then-filter-in-Rust style of
// backend/src/services/background_jobs.rs:184-368 (process_missed_tasks)
async fn build_missed_yesterday_section(
    pool: &SqlitePool,
    household_id: &Uuid,
    user_id: &Uuid,
    settings: &HouseholdSettings,
    yesterday: NaiveDate,
) -> Result<Vec<String>, ReportError> {
    let mut titles = Vec::new();

    // D-08/D-09: penalties actually applied, excluding inverted habits (those got a reward, not a penalty)
    let penalty_task_ids: Vec<String> = sqlx::query_scalar(
        "SELECT task_id FROM missed_task_penalties WHERE due_date = ?",
    )
    .bind(yesterday)
    .fetch_all(pool)
    .await?;

    for task_id_str in penalty_task_ids {
        if let Ok(task_id) = Uuid::parse_str(&task_id_str) {
            if let Some(task) = tasks_service::get_task(pool, &task_id).await? {
                if task.archived || task.paused { continue; }                       // D-14 "everywhere"
                if task.suggestion.is_some() && task.suggestion != Some(shared::SuggestionStatus::Approved) { continue; } // D-14 — see Pitfall #7, NOT guaranteed by the source table
                if task.recurrence_type == shared::RecurrenceType::OneTime { continue; } // D-14 missed-only exclusion
                if task.habit_type.is_inverted() { continue; }                       // D-09
                let is_mine = task.assigned_user_id.map(|id| id == *user_id).unwrap_or(true); // D-13
                if !is_mine { continue; }
                titles.push(task.title);
            }
        }
    }

    // D-10: inverted habits performed yesterday (raw task_completions check, not period-bounds-based)
    if !household_settings::is_household_on_vacation(settings, yesterday) { // see Open Question #1
        let completed_bad_habits: Vec<(String,)> = sqlx::query_as(
            r#"
            SELECT t.title FROM task_completions tc
            JOIN tasks t ON tc.task_id = t.id
            WHERE tc.due_date = ? AND t.habit_type = 'bad'
              AND t.archived = 0 AND t.paused = 0
              AND (t.suggestion IS NULL OR t.suggestion = 'approved')
              AND t.recurrence_type != 'onetime'
              AND (t.assigned_user_id = ? OR t.assigned_user_id IS NULL)
            "#,
        )
        .bind(yesterday)
        .bind(user_id.to_string())
        .fetch_all(pool)
        .await?;
        titles.extend(completed_bad_habits.into_iter().map(|(t,)| t));
    }

    titles.sort_by_key(|t| t.to_lowercase());
    Ok(titles)
}
```

### Pattern 5: Text formatting (D-20/D-21/D-22/D-23)
```rust
fn format_report(household_name: &str, today: NaiveDate, due_today: &[ReportLine], missed_yesterday: &[String]) -> String {
    let header = format!("Daily report — {} — {}", household_name, today.format("%a, %Y-%m-%d"));
    // chrono's %a/%A are English by default (no locale feature enabled in this workspace's
    // Cargo.toml — only `features = ["serde"]` for chrono) — verified against chrono 0.4.43 docs.

    let due_body = if due_today.is_empty() {
        "No tasks scheduled for today".to_string()
    } else {
        due_today.iter().map(format_due_line).collect::<Vec<_>>().join("\n")
    };

    let missed_body = if missed_yesterday.is_empty() {
        "All tasks completed yesterday".to_string()
    } else {
        missed_yesterday.iter().map(|t| format!("- {}", t)).collect::<Vec<_>>().join("\n")
    };

    format!("{header}\n\nDue today:\n{due_body}\n\nMissed yesterday:\n{missed_body}")
}

fn format_due_line(line: &ReportLine) -> String {
    let mut s = format!("- {}", line.title);
    if let Some(t) = &line.due_time { s.push_str(&format!(" (by {})", t)); }
    if line.done { s.push_str(" (done)"); }
    s
}
```

```rust
pub async fn copy_to_clipboard(text: &str) -> Result<(), String> {
```

### Anti-Patterns to Avoid
- **Calling `tasks::get_due_tasks` from the report:** explicitly rejected by D-05 — it uses `Utc::now().date_naive()` (UTC, not household-timezone). Build the report's own due-today computation instead.
- **Recomputing "was this task missed" for the missed-yesterday section:** rejected by D-08 — read `missed_task_penalties`, do not re-run `is_task_due_on_date` + `is_task_overdue` for yesterday from scratch.
- **Calling `scheduler::today_in_timezone(tz)` inside the report service:** makes the function's output depend on the real wall clock at test time — see Common Pitfall #5.
- **Using `document.execCommand("copy")`:** deprecated DOM API; use `web_sys::Clipboard` instead (see Alternatives Considered).

## Don't Hand-Roll

| Problem                                            | Don't Build                                                  | Use Instead                                                                 | Why                                                                                                   |
| ----------------------------------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Timezone-aware "today"/"yesterday"                 | A new date/timezone parsing helper                            | `scheduler::parse_timezone` + inline `now_utc.with_timezone(&tz).date_naive()`   | Already exists, already unit-tested for the "not-yet-created" edge case and recurrence-type edge cases |
| "Is this task due on date X"                       | Reimplementing recurrence-type switch logic                   | `scheduler::is_task_due_on_date`                                                 | D-03 names it explicitly; ~20 existing unit tests cover every `RecurrenceType` variant                  |
| "Is this a bad habit"                              | Checking `task.habit_type == HabitType::Bad` inline everywhere | `task.habit_type.is_inverted()`                                                  | Single source of truth, already used by `background_jobs.rs` and `tasks.rs`                             |
| Vacation-mode date-range check                     | Comparing `vacation_start`/`vacation_end` manually              | `household_settings::is_household_on_vacation`                                  | Already handles all four `(start, end)` `Option` combinations, already unit-tested                      |
| Household-membership authorization                 | A new middleware / extractor                                  | The existing manual `extract_user_id` + `is_member` two-liner                   | This literally is the only pattern in the codebase (see Common Pitfall #1) — introducing a new one would be inconsistent, not an improvement |
| Copy-to-clipboard                                  | A hand-rolled `<textarea>` + `execCommand` shim, or a new crate | `web_sys::Clipboard` + `wasm_bindgen_futures::JsFuture` (already-present deps)   | Standard, already-available, requires only two feature-flag additions                                   |

**Key insight:** This phase's biggest risk is not "which library to use" (there are none to choose) but **silently reimplementing logic that already exists in a subtly different, wrong way** — the report must produce output consistent with what the background job already decided (D-08's whole premise), and consistency comes from reusing the same functions, not reimplementing lookalikes.

## Common Pitfalls

### Pitfall 1: `AuthenticatedUser` extractor does not exist
**What goes wrong:** `CLAUDE.md` and `.planning/codebase/STRUCTURE.md` both describe handlers as extracting auth "via an `AuthenticatedUser` extractor." A planner trusting these docs literally would try to write `async fn get_report(user: AuthenticatedUser, ...)`.
**Why it happens:** The docs describe an aspirational/older convention that was never implemented (or was refactored away) — verified by `grep -rn "AuthenticatedUser" backend/src/` returning **zero** matches anywhere in the codebase.
**How to avoid:** Every single handler (`tasks.rs`, `statistics.rs`, `households.rs`, ...) uses the identical manual pattern instead:
```rust
let user_id = match crate::middleware::auth::extract_user_id(&req, &state.config.jwt_secret) {
    Ok(id) => id,
    Err(_) => return Ok(HttpResponse::Unauthorized().json(ApiError { .. })),
};
```
followed by an explicit `household_service::is_member(...)` check. Copy this pattern verbatim (see Pattern 1 above).
**Warning signs:** Any compile error referencing an undefined `AuthenticatedUser` type.

### Pitfall 2: SQLx compile-time macros are not used anywhere — `cargo sqlx prepare` is not part of this phase
**What goes wrong:** `.planning/codebase/STRUCTURE.md` states `backend/sqlx-data.json: SQLx offline query data (regenerate with cargo sqlx prepare)`, and `CLAUDE.md` says the backend "Uses `SQLX_OFFLINE=true` for compile-time query checking." A planner trusting this would add a "run `cargo sqlx prepare`" step after adding the report's queries.
**Why it happens:** `SQLX_OFFLINE=true` **is** set (verified: `default.nix:14` and `flake.nix:141`), but `grep -rn "sqlx::query!|sqlx::query_as!|sqlx::query_scalar!" backend/src/` returns **zero** matches in the entire backend. Every single query in this codebase uses the **runtime** forms — `sqlx::query(...)`, `sqlx::query_as::<_, T>(...)`, `sqlx::query_scalar::<_, T>(...)` — which are never checked against a live database at compile time regardless of `SQLX_OFFLINE`. There is also no `backend/sqlx-data.json` or `.sqlx/` directory anywhere in the repo (verified — neither exists).
**How to avoid:** Write the report's queries using the same runtime `sqlx::query_as(...)` / `sqlx::query_scalar(...)` forms as every other query in the codebase (see Code Examples). Do **not** add a `cargo sqlx prepare` task to the plan — there is nothing to regenerate.
**Warning signs:** None — this only matters if a task is written assuming a workflow step that doesn't apply.

### Pitfall 3: The shared test harness has no `missed_task_penalties` table
**What goes wrong:** A report-service test that inserts a row into `missed_task_penalties` (as CONTEXT.md's own landmine note requires — "Tests must insert the rows explicitly") will fail with a SQLite "no such table" error if it uses `test_utils::create_test_pool()` as-is.
**Why it happens:** Verified directly: `backend/src/test_utils.rs::create_test_schema()` creates 15 tables (`users`, `households`, `household_settings`, `user_settings`, `household_memberships`, `task_categories`, `tasks`, `task_completions`, `task_period_results`, `point_conditions`, `task_consequences`, `rewards`, `punishments`, `task_rewards`, `task_punishments`, `user_rewards`, `user_punishments`, `activity_logs`) — `missed_task_penalties` is not among them. It is also absent from `background_jobs.rs`'s own **separate**, module-local `setup_test_db()` (used only by that file's own tests), so there is no existing schema anywhere in the test suite to copy from except the production migration.
**How to avoid:** Add this to `test_utils.rs::create_test_schema()` before writing report tests (exact DDL from the production migration, `backend/migrations/20240125000000_missed_task_tracking.sql`):
```rust
sqlx::query(

    CREATE TABLE IF NOT EXISTS missed_task_penalties (

```
Also add a fixture helper mirroring the existing style (e.g. `link_task_reward`):

### Pitfall 4: The shared test harness's `household_settings` table is missing 16 of 22 production columns
**What goes wrong:** `household_settings::get_or_create_settings(pool, household_id)` runs `SELECT * FROM household_settings WHERE household_id = ?` mapped via `sqlx::query_as::<_, HouseholdSettingsRow>`. `HouseholdSettingsRow` (`backend/src/models/household_settings.rs:9-32`) has **22 fields**. `test_utils.rs::create_test_schema()`'s `household_settings` table (lines ~74-90) has only **7 columns**: `household_id, timezone, hierarchy_type, vacation_mode, auto_archive_days, created_at, updated_at` (note: `created_at` isn't even a production column — the real migration only has `updated_at`). This means calling `get_or_create_settings` against a `test_utils::create_test_pool()` pool will fail at runtime with a column-not-found error from `FromRow`, because `dark_mode`, `role_label_owner`, `role_label_admin`, `role_label_member`, `rewards_enabled`, `punishments_enabled`, `chat_enabled`, `vacation_start`, `vacation_end`, `allow_task_suggestions`, `week_start_day`, `default_points_reward`, `default_points_penalty`, `solo_mode`, `solo_mode_exit_requested_at`, `solo_mode_previous_hierarchy_type` (16 columns) do not exist in the test table.
**Why it happens:** This table was apparently built early (Phase 2, task/period-tracking focus) before household-settings-dependent testing (vacation mode, timezone) was needed by that phase's own scope; `background_jobs.rs` worked around it by building its **own**, separate, full-column local schema (`background_jobs.rs`'s private `setup_test_db()`, lines ~658-877, which **does** have all 22 columns) rather than fixing the shared harness — likely exactly because TEST-04 (background job tests) is still marked "Pending" in `REQUIREMENTS.md`/`STATE.md` and this gap was never reconciled.
**How to avoid:** Extend `test_utils.rs`'s `household_settings` CREATE TABLE statement to the full 22-column production schema (copy from `background_jobs.rs`'s own local `setup_test_db()`, which already has the correct, complete DDL) **before** writing any report-service test that calls `get_or_create_settings` or otherwise depends on non-timezone/vacation settings fields. This is a prerequisite for RPT-04 ("service ... covered by tests"), not optional polish.
**Warning signs:** `sqlx::Error::ColumnNotFound("dark_mode")` (or similar) when a report test touches household settings.

### Pitfall 5: `scheduler::today_in_timezone()` hardcodes `Utc::now()` — it is not mockable
**What goes wrong:** It's tempting to write `let today = scheduler::today_in_timezone(tz);` inside the report service, matching the "obvious" reading of D-04. This compiles and works, but silently makes the function's result depend on the real wall-clock at the moment the test runs, defeating the "pass current_date as a parameter" testing convention.
**Why it happens:** `scheduler::today_in_timezone(tz: Tz) -> NaiveDate` is implemented as `Utc::now().with_timezone(&tz).date_naive()` (`scheduler.rs:326-328`) — it takes no "now" parameter at all.
**How to avoid:** Give `generate_daily_report` a `now_utc: DateTime<Utc>` parameter (see Pattern 2) and inline the one-line computation (`now_utc.with_timezone(&tz).date_naive()`) instead of calling `today_in_timezone`. This is directly precedented by `scheduler::is_task_overdue`, which already takes `now_utc: DateTime<Utc>` as an explicit parameter for exactly this reason.
**Warning signs:** Report tests that pass around midnight household-time or near month/year boundaries become flaky.

### Pitfall 6: `Weekdays`/`Custom` recurrence completions can be recorded with a due_date that isn't "today"/"yesterday"
**What goes wrong:** `tasks_service::complete_task` computes the completion's stored `due_date` via `scheduler::get_next_due_date(&task, today)` (`tasks.rs:663,699`). For `RecurrenceType::Daily`, `Weekly`, and `Monthly`, if today is itself the scheduled day, `get_next_due_date` correctly returns **today** (verified in `scheduler.rs:136,138-157,159-185` and their tests). But for `RecurrenceType::Weekdays` (`scheduler.rs:187-211`) and `RecurrenceType::Custom` (`scheduler.rs:213-226`), the implementation **deliberately skips today** even when today is a scheduled/matching day, and returns the *next* occurrence instead (explicitly tested: `test_get_next_due_date_weekdays` asserts "When completing on Monday, should get NEXT Monday, not today"). This means a Weekdays/Custom task completed exactly on its due day can be stored with `due_date` = a future date, not today.
**Why it happens:** Pre-existing scheduler design (not something to fix in this phase — same spirit as the deferred `get_due_tasks` UTC bug).
**How to avoid:**
- For the D-07 "done today" marker: do **not** use a raw `task_completions WHERE due_date = today` check (it will miss Weekdays/Custom completions). Instead mirror `tasks_service::get_task_with_status`'s own `completions_today` computation (`tasks.rs:137-152`): compute `period_date = get_next_due_date(task, today).unwrap_or(today)`, then `get_period_bounds(task, period_date)`, then count completions in that range. This is also what the rest of the UI already uses to show "done" state, so the report stays visually consistent with the Tasks page.
- For D-10 (raw `task_completions.due_date = yesterday` on an inverted-habit task, as CONTEXT.md literally specifies): implement it exactly as worded. This inherits the same theoretical gap for Weekdays/Custom bad habits, but D-10's wording is a locked decision naming `due_date = yesterday` explicitly, and "fixing" only this one query would create an internal inconsistency with D-08 (which trusts the background job's own, same-flavored bookkeeping). Flagged as a known limitation, not a defect to fix in this phase.
**Warning signs:** A Weekdays or Custom-recurrence task completed today doesn't show `(done)` in the report even though the Tasks page shows it as completed (this would indicate the naive `due_date = today` check was used instead of the period-bounds approach).

### Pitfall 7: `process_missed_tasks` does not filter by suggestion status — the report's own join must
**What goes wrong:** D-14 states exclusions "mirror the background job," including "pending suggestions are excluded everywhere," implying `missed_task_penalties` never contains rows for suggested-but-not-approved tasks.
**Why it happens:** Reading `background_jobs.rs::process_missed_tasks` (lines 194-198) line by line: it fetches with a bare `SELECT * FROM tasks` and the loop only checks `recurrence_type == OneTime`, `paused`, and `archived` — there is **no** `suggestion` filter. Compare this to its siblings in the same file, `process_auto_archive` (line 401: `... AND (suggestion IS NULL OR suggestion = 'approved')`) and `process_period_finalization` (line 536: same clause) — both of which **do** filter suggestions. `process_missed_tasks` is the odd one out.
**How to avoid:** Do not assume `missed_task_penalties` is already suggestion-clean. The report's own join from `missed_task_penalties`/`task_completions` back to `tasks` must apply the `suggestion IS NULL OR suggestion = 'approved'` filter explicitly (shown in Code Examples, Pattern 4) to honor D-14, rather than relying on the source table having already excluded these rows.
**Warning signs:** None directly observable without a task that was suggested, not yet approved, and somehow due yesterday — a rare edge case, but the filter costs nothing to add defensively and is what D-14 asks for.

### Pitfall 8: Missing `web-sys` features will fail the frontend build, not just clipboard calls
**What goes wrong:** Adding `window.navigator().clipboard().write_text(...)` without first adding `"Clipboard"` and `"Navigator"` to the `web-sys` feature list causes a compile error (missing method / missing type), not a runtime error.
**Why it happens:** The workspace's current `web-sys` feature list (`Cargo.toml`, `[workspace.dependencies]`) is `["Window", "Document", "HtmlInputElement", "WebSocket", "MessageEvent", "CloseEvent", "Location", "BinaryType", "ErrorEvent"]` — verified directly, no `Clipboard` or `Navigator` present. No existing frontend code uses the Clipboard API (verified: zero matches for "clipboard" anywhere in `frontend/src/`), so this has never been needed before now.
**How to avoid:** Add both feature strings to the `web-sys` entry before writing any clipboard code; this must be an early task in the plan (or the very first frontend task), since everything else in the same crate fails to compile until it's done.
**Warning signs:** `error[E0599]: no method named 'clipboard' found for struct 'web_sys::Navigator'` or similar.

## Open Questions

1. **Does D-14's "household vacation days are additionally excluded" (missed-yesterday section) apply to the D-10 half (inverted habits performed yesterday), or only to the `missed_task_penalties` half?**
   - What we know: `missed_task_penalties` rows are naturally vacation-clean by construction — `process_missed_tasks` skips writing a penalty row when the household is on vacation, so D-08's half of the section needs no extra vacation check. `task_completions` (D-10's source) has **no** vacation-awareness at all — `complete_task` never checks vacation mode, so a user can complete/indulge a bad habit during vacation and it will land in `task_completions` regardless.
   - What's unclear: CONTEXT.md's D-14 wording scopes the vacation exclusion to "the missed yesterday section" as a whole, but the two data sources behave differently (one is naturally clean, one is not).
   - Recommendation: apply `household_settings::is_household_on_vacation(&settings, yesterday)` as an explicit guard around the D-10 query too (shown in Code Examples, Pattern 4), for internal consistency with D-14's stated intent for the section as a whole. This is a one-line, low-risk addition; flagging it here so the planner/reviewer can confirm the interpretation matches user intent.

2. **Sort order within "due today" (Claude's discretion, per CONTEXT.md) — the proposed "consistent with `get_all_tasks_with_status`" doesn't quite transfer.**
   - What we know: `get_all_tasks_with_status` sorts by `next_due_date` (a `NaiveDate`), then title. But every task in the "due today" section shares the *same* `next_due_date` (today), so sorting by that field would be a no-op.
   - What's unclear: whether the user's intent (referencing that function) was "same tie-break style" (title, case-insensitive) rather than literally the same primary key.
   - Recommendation: sort by `due_time` ascending (tasks without a `due_time` sort last, consistent with `parse_due_time`'s "no due_time = end of day/23:59" default elsewhere in the codebase), then title as the tiebreaker (matching the case-insensitive title tiebreak style used everywhere else). This gives a "what's due soonest" ordering, which is more useful within a single day than an arbitrary tiebreak-only sort.

3. **Does D-21's "show the deadline time if `due_time` is set" apply to both sections, or only "due today"?**
   - What we know: D-20's worked example only shows a `due_time` suffix in the "Due today" section; the "Missed yesterday" example line ("- Vacuuming") has no time shown, but that could simply be because the example task has no `due_time` set, not because the rule doesn't apply there.
   - What's unclear: D-21 states the rule generally ("Per task, show the title plus the deadline time...") without scoping it to one section.
   - Recommendation: apply the same `format_due_line`-style formatting uniformly to both sections (one shared helper, shown in Pattern 5) — simpler, more consistent, and nothing in CONTEXT.md suggests deliberately differentiating.
