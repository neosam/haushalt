<assumptions>
- **A-20 (D-20/D-21, C-4 closed):** the section is a new block on `HouseholdSettingsPage`, placed
  **outside** every `<Show when=…can_manage_tasks()>` / `is_owner` guard, so every member sees their
  own. No route guard changes. It is labelled as the member's *personal* settings for this household,
  to distinguish it from the household-wide administrative blocks above it.
- **A-21 (A-17 continued):** two-step target selection. The member saves the key, presses
  "Load targets", picks a name, saves again. The browser never holds the key beyond the one PUT
  (D-22), and the picker is populated by our backend, not by a cross-origin call to nomi.ai.
- **A-22:** the API key input starts empty on every load and is never populated from the response —
  there is nothing in `NomiConnection` to populate it with (D-09). Submitting the form with the field
  empty leaves the stored key untouched; the dedicated "clear key" action sends
  `enabled: Some(false)` together with `api_key: Some("")`, matching the single write the service
  performs (W-3).
- **A-23:** target list caching is none — the list is fetched when the member presses the button
  (explicitly Claude's discretion in D-05). `target_name` from the connection is shown until then, so
  a renamed Nomi displays a stale name until the next load. Accepted.
- **A-24:** a room whose `status` is `"Creating"` is shown with a hint in the picker, because that is
  exactly the state that produces `RoomStillCreating` on send.
</assumptions>
