<assumptions>
- **A-05 (enabled vs configured, RESEARCH Open Question 3):** `enabled = true` is refused unless the
  row will hold both an `api_key_encrypted` and a `target_uuid` after the update is applied. The
  check lives in `update_connection` only, and is unit-tested. Removing the key is the one operation
  that resolves the same invariant by switching the connection **off** instead of refusing, so the
  "remove key" button in plan 05-05 can never dead-end (W-3). A connection that loses its key later
  keeps `enabled = 1` and simply fails with a recorded `last_error` — see A-06.
- **A-06 (RESEARCH Open Question 2):** a decryption failure (key rotated, state dir wiped) does not
  auto-disable the connection. It writes `last_error` and leaves `enabled` alone, so the user sees
  the cause in the UI and only has to re-enter the key.
- **A-07:** `UpdateNomiConnectionRequest.api_key` is write-only and tri-state: absent ⇒ unchanged,
  `Some(non-empty)` ⇒ re-encrypted with a fresh nonce, `Some("")` ⇒ cleared to NULL **and**
  `enabled = 0` in the same write. There is no read path for it at all, and the type has a
  hand-written redacting `Debug` because it is the only one in the phase carrying the plaintext.
- **A-08:** `NomiConnectionRow` derives neither `Serialize` nor `Deserialize`. A row can therefore
  not be returned from a handler by accident; only `to_shared()` output can.
</assumptions>
